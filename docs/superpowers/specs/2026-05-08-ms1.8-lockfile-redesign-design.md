# MS1.8 — Lockfile redesign (YAML → JSON, merge-friendly, schema-versioned)

**Status**: Spec, awaiting plan
**Date**: 2026-05-08
**Author**: pair (Aperrix + Claude)

**Inspired by**: [vercel-labs/skills](https://github.com/vercel-labs/skills) `local-lock.ts` design (commit-pinned analysis from 2026-05-08)

## Context

The runtime currently writes a per-project lockfile at `<cwd>/.aiactions/lock.yaml` via `appendLockfileEntry` in `packages/runtime/src/runner/uses/registry-fetch.ts`. Each entry stores `resolved-sha` and `fetched-at` for an action coordinate `<ns>/<name>@<ver>`. The file is **write-only today**; no code reads it. Read-back is a prerequisite for MS1.9 (`aia workflow run` / restore-from-lockfile semantics).

The current shape has four design issues that surface once we plan to read the file and once consumer projects start committing it:

1. **YAML quoting pitfalls.** The code already comments that "YAML 1.2's number-coercion rules" forced manual quoting of SHAs and timestamps. JSON eliminates the class of bug.
2. **`fetched-at` baked into a committed file** produces merge conflicts whenever two branches install the same action in parallel — timestamps disagree per branch.
3. **No `version` field.** Schema evolution has no upgrade path; today the only option is "ship a breaking change and pray downstream lockfiles aren't relied on".
4. **Per-entry timestamps mix two concerns** — dependency pinning (project state) and audit history (run-time). The latter belongs in a separate run-log artefact (deferred, out of scope).

The vercel-labs/skills project hit the same trade-offs and converged on a **JSON, version-tagged, timestamp-free, alphabetically-sorted, empty-on-parse-fail** local lockfile. Their design is the prior art we adopt here, simplified to AIactions' single-registry MVP.

## Goals

- **G1**: Lockfile is JSON, schema-versioned, merge-conflict resilient.
- **G2**: Read API exists and is robust (never throws on malformed data; returns empty struct on any recoverable error).
- **G3**: Writer is deterministic — same input produces byte-identical output.
- **G4**: Module is a clean SRP boundary (`packages/runtime/src/lockfile.ts`), reusable from CLI for the future restore primitive.
- **G5**: Pre-1.0 wipe-on-mismatch policy avoids any migration code; any non-current schema is treated as empty.

## Non-goals

- **NG1**: Restore primitive (`aia action install` no-arg → reinstall from lockfile). Deferred to a follow-up milestone — has its own UX, picker, conflict resolution.
- **NG2**: Drift detection (`aia action audit` → re-resolve `@ver` and warn on SHA divergence). Deferred — separate command, separate concerns.
- **NG3**: Run logs / audit history (per-run JSONL or SQLite at `~/.aiactions/runs/`). Out of scope; brainstorm a separate milestone if/when the use case lands.
- **NG4**: Per-user state file (XDG state, dismissed prompts, `lastSelectedAgents`). YAGNI until first concrete use case.
- **NG5**: Multi-source registry support. Today the canonical registry is fixed (`aperrix/aiactions`). When pluggable sources arrive, schema bumps to `version: 2` (adds `sourceUrl` per entry) — wipe-on-mismatch handles legacy.

## Design

### File path

```
<cwd>/.aiactions/lock.json
```

Rationale: keep the `.aiactions/` namespace for future per-project state (run logs, caches) without forcing a directory rename later. Single-file YAGNI rejected because consumer projects may eventually accumulate AIactions-owned per-project files; reserving a dedicated dir now costs nothing and avoids a future mass migration of consumer projects.

### Schema (v1)

```jsonc
{
  "version": 1,
  "actions": {
    "claude/agent@1.0.0": {
      "resolvedSha": "28232816d97369292e6080fed122a820510d7f0a"
    }
  }
}
```

**File-level fields**

- `version: number` — schema version, currently `1`. Wipe-on-mismatch on any other value.
- `actions: Record<string, { resolvedSha: string }>` — map of action coordinate to pinned entry.

**Per-entry fields (minimal)**

- `resolvedSha: string` — git SHA the registry resolved `<ns>/<name>@<ver>` to at install time. 40-char lowercase hex.

**Explicitly absent fields and why**

| Field | Why absent |
|---|---|
| `fetched-at` / `installedAt` / `updatedAt` | Merge-conflict source on parallel installs; AIactions has no current consumer of timestamps. Belongs in run-log if ever needed. |
| `sourceUrl` | Single canonical registry today; URL is implicit. v2 adds it on multi-source rollout. |
| `skillPath` / actionPath | Path is deterministic from coordinate (`actions/<ns>/<name>`). Storing it duplicates registry knowledge. |
| `pluginName` (vercel) | AIactions has no plugin abstraction. |
| `dismissed` / `lastSelectedAgents` (vercel) | Per-user UI state, not project state. Deferred (NG4). |

**Naming convention**: camelCase JSON-style (`resolvedSha`). Aligned with the JS lockfile ecosystem (`package-lock.json`, `bun.lock`).

### Module structure

New file: `packages/runtime/src/lockfile.ts`

Existing call site `packages/runtime/src/runner/uses/registry-fetch.ts` migrates from inline `appendLockfileEntry` to importing from the new module.

### API surface

```ts
import type { RegistryCoordinate } from "./runner/uses/registry-fetch.ts";

export interface LockfileEntry {
  readonly resolvedSha: string;
}

export interface LockfileShape {
  readonly version: 1;
  readonly actions: Record<string, LockfileEntry>;
}

export interface UpsertLockfileEntryRequest {
  readonly cwd: string;
  readonly ref: RegistryCoordinate;
  readonly resolvedSha: string;
}

/** Read `<cwd>/.aiactions/lock.json`. Never throws on malformed data — returns empty struct. */
export function readLockfile(cwd: string): Promise<LockfileShape>;

/** Write `<cwd>/.aiactions/lock.json` deterministically (sorted, trailing newline). Throws on FS errors. */
export function writeLockfile(cwd: string, lock: LockfileShape): Promise<void>;

/** Idempotent upsert. Reads → mutates → writes in one call. */
export function upsertLockfileEntry(req: UpsertLockfileEntryRequest): Promise<void>;
```

`RegistryCoordinate` is the existing type from `@aiactions/runtime` (defined in `packages/runtime/src/runner/uses/registry-fetch.ts:26` and re-exported from `packages/runtime/src/index.ts:10`). Shape: `{ namespace: string; name: string; version: string }`. The lockfile key is `${namespace}/${name}@${version}`.

Once `lockfile.ts` becomes the SRP owner of the lockfile concern, consider relocating the `RegistryCoordinate` definition there (or to a shared types module) and re-exporting from `registry-fetch.ts` for backward compatibility — flagged as a plan-level decision, not a spec requirement.

### Read semantics

```
readLockfile(cwd):
  1. read <cwd>/.aiactions/lock.json (utf8)
  2. on ENOENT     → return EMPTY
  3. on other FS error (EACCES, EIO) → throw (fail-fast)
  4. JSON.parse → on error → return EMPTY
  5. zod safeParse against schemaV1 → on fail → return EMPTY
  6. return parsed value
```

`EMPTY = { version: 1, actions: {} }`.

The empty-on-fail behaviour intentionally swallows parse errors and version mismatches — this is the **wipe-on-mismatch** policy. It also recovers automatically from git merge-conflict markers (file becomes invalid JSON during a conflicted merge → next read returns empty → next install rebuilds from registry).

Real FS errors (permission denied, IO error) still propagate so the user sees them.

### Write semantics

```
writeLockfile(cwd, lock):
  1. mkdir -p <cwd>/.aiactions
  2. sort lock.actions keys alphabetically (deterministic order)
  3. JSON.stringify(sorted, null, 2) + '\n'   // 2-space indent, trailing newline
  4. writeFile <cwd>/.aiactions/lock.json (utf8)
  5. throws on any FS error
```

The trailing newline is non-negotiable: most linters and `git diff` tooling treat its absence as a defect.

### Upsert semantics

```
upsertLockfileEntry({cwd, ref, resolvedSha}):
  1. lock = await readLockfile(cwd)
  2. key = `${ref.namespace}/${ref.name}@${ref.version}`
  3. lock.actions[key] = { resolvedSha }
  4. await writeLockfile(cwd, lock)
```

Idempotent: same ref called twice → one entry, last write wins. Other entries preserved (read-then-write; no truncation).

### Validation (zod)

```ts
import { z } from "zod";

const lockfileEntrySchema = z.object({
  resolvedSha: z.string(),
}).strict();

const lockfileSchemaV1 = z.object({
  version: z.literal(1),
  actions: z.record(z.string(), lockfileEntrySchema),
}).strict();
```

`.strict()` on both — unknown fields fail validation. This matches the wipe-on-mismatch policy: a downgrade reading a v2 file with extra fields gets `EMPTY` and rebuilds. Forward-compat is bought at the cost of one extra registry resolution; cheaper than maintaining migration code.

### Migration

Pre-1.0, no public consumers. The legacy `<cwd>/.aiactions/lock.yaml` files in development checkouts are wiped automatically on next install:

- Old YAML file present → `readLockfile` opens `lock.json` → ENOENT → empty struct.
- Next install writes `lock.json`.
- Old `lock.yaml` is left in place but ignored. Cleanup (delete the file) is a one-line manual step or covered by the project-level `.gitignore` of `.aiactions/`.

`appendLockfileEntry`, the local `LockfileShape` interface, and the local `parseYaml` import in `registry-fetch.ts` are deleted as part of this milestone. The `yaml` package dependency is kept (still used by `@aiactions/workflows` for parsing `aiaction.yaml` and workflow files).

### Concurrency

Single writer per project (one workflow run at a time). No file lock, no atomic-rename gymnastics. If parallel runs against the same `cwd` ever become a thing, revisit with one of:

- Advisory file lock (`flock(2)`)
- Atomic write via `<file>.tmp` + rename
- Switch to per-run state files

Out of scope today; flag in a code comment for future readers.

### Self-host (`.aiactions/` in this repo)

The AIactions repo dogfoods. The `.aiactions/lock.json` file generated by smoke runs is a transient artefact, not shared state. Add `.aiactions/` to the repo's `.gitignore`. Downstream consumer projects make the opposite choice (commit the lockfile for reproducibility, like `bun.lock` or `package-lock.json`).

## Tests

Test file: `packages/runtime/tests/lockfile.test.ts`. Cover real failure modes only.

**Round-trip + determinism**

- Write → read → struct identical.
- Write same lockfile twice → byte-identical output (sort + format stable).
- Output ends with `\n`.

**Wipe-on-mismatch / recovery**

- ENOENT → `EMPTY`.
- Legacy YAML content → `EMPTY` (JSON.parse fails).
- File with `version: 0` → `EMPTY`.
- File with merge-conflict markers (`<<<<<<<`) → `EMPTY`.
- Malformed JSON (truncated, garbage) → `EMPTY`.

**Validation**

- `{ actions: "not-an-object" }` → `EMPTY`.
- Entry without `resolvedSha` → `EMPTY`.
- Entry with extra unknown field (`.strict()`) → `EMPTY` (forward-compat = wipe + rebuild).

**Upsert**

- Same ref called twice → one entry, last value wins.
- Different refs → both preserved, alphabetically ordered on disk.

**Out of scope**

- mkdir behaviour (delegated to `node:fs`).
- `JSON.stringify` behaviour (delegated to runtime).
- Disk-full / permission errors (FS-level, propagated to caller — caller's job).

The existing `packages/runtime/tests/runner-uses-registry-fetch-lockfile.test.ts` file is deleted; its assertions are reborn in the new test file against the new API.

## Risks and trade-offs

- **No reader of the lockfile after this milestone**, so the redesign by itself produces zero observable behaviour change for end users. The win lands when MS1.9 reads it. **Mitigation**: ship as a precursor; tests verify the read path now to protect MS1.9 from a brittle baseline.
- **Wipe-on-mismatch loses history.** Any time we bump `CURRENT_VERSION`, all consumer projects re-resolve every action on next install. **Mitigation**: bump rarely; bumps require justification in the commit message + a CHANGELOG note.
- **`.strict()` zod schema is forward-incompatible**: a v1 client cannot read a v2 file even if all v1 fields are present. Trade-off accepted: explicit wipe is cleaner than partial-parse semantics.
