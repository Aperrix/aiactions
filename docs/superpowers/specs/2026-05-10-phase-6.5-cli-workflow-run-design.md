# Phase 6.5 — `aia workflow run` slice

**Status**: Design (locked through brainstorm 2026-05-10)
**Predecessor**: Phase 6 (`docs/superpowers/specs/2026-05-10-phase-6-cli-workflow-slices-design.md`) — workflow list + check
**Successor**: TBD (likely a workflow-run polish phase: colors, `--quiet`, `--env-file`, etc.)

## 1. Goal

Add the third and final workflow slice to `@aiactions/cli`: `aia workflow run`. This is the verb that actually executes a workflow on the local machine, wrapping `runWorkflow()` from `@aiactions/core` with CLI-grade ergonomics: workflow resolution (discovered name vs file path), inputs / env from argv, working directory, lifecycle rendering (pretty + NDJSON), exit-code mapping from `RunResult`, and signal forwarding (Ctrl-C / SIGTERM → graceful abort).

## 2. Non-goals

- No `--quiet` / silent mode (YAGNI; users can `2>/dev/null`).
- No `--watch` mode (re-run on file change).
- No ANSI color output (only emojis: `▶ ✓ ✗ ▼`).
- No `--env-file <path.env>` or `--inputs-file <path.json>` (YAGNI).
- No multi-SIGINT escalation / force-kill mode.
- No new `workflow-cancelled` `RuntimeEvent` kind (would be a `feat(schema)!` BREAKING; cancellation is signalled by exit code 130 + the absence of further events).

## 3. Constraints

- Local-only runtime — `runWorkflow` runs on the developer's machine. No network proxying, no remote runner. (AIactions hard constraint.)
- ESM-only, Bun workspace, strict TypeScript, no `any`.
- Must compose with existing brick packages — `@aiactions/core`, `@aiactions/discovery`, `@aiactions/parser`, `@aiactions/schema`, `@aiactions/paths`. No inlining of runtime logic.
- All AIactions errors must surface through the existing `CliError` / `AIactionsError` / `EXIT_BY_BRICK_ERROR` plumbing in `cli/_shared/`.
- Single-component PR (only `@aiactions/cli` changes) — merged with `git merge --no-ff` for per-commit Conv Commit history (preferred over squash to match phase-6 pattern).

## 4. Architecture

### 4.1 File layout

```
packages/cli/src/commands/workflow/
  index.ts                      # add `run: runCommand` to subCommands
  list/                         # (phase 6, unchanged)
  check/                        # (phase 6, unchanged)
  run/
```

### 4.4 Sharing rule

`parse-kv.ts` is intentionally co-located in the slice rather than `_shared/` even though it is consumed twice (inputs + env). Rule of three is not met (one slice, two callsites internally). Extraction triggers when a third caller emerges.

The slice does not introduce any other shared helpers — `resolve-workflow.ts` is single-use within the slice.

## 5. citty args

```ts
{
  name: {
    type: "positional",
    description: "Discovered workflow name (looked up via discoverWorkflows())",
    required: false,
  },
  file: {
    type: "string",
    description: "Path to a workflow YAML file (overrides discovery)",
    required: false,
    valueHint: "<path>",
  },
  input: {
    type: "string",
    description: "Workflow input k=v (repeatable). Example: --input branch=main",
    required: false,
    alias: "i",
    valueHint: "<k=v>",
  },
  env: {
    type: "string",
    description: "Extra env var k=v layered above workflow.env (repeatable)",
    required: false,
    alias: "e",
    valueHint: "<k=v>",
  },
  cwd: {
    type: "string",
    description: "Working directory (default: process.cwd())",
    required: false,
    valueHint: "<path>",
  },
  json: {
    type: "boolean",
    description: "Emit NDJSON event stream on stdout instead of pretty output",
    default: false,
  },
}
```

### 5.1 Argument validation

Performed in the slice orchestrator (`run-workflow.ts`), not in `command.ts`:

| Condition | Result |
|---|---|
| no `<name>` AND no `--file` | `UsageError("expected <name> or --file")` → `EXIT.USAGE` (2) |
| `<name>` AND `--file` | `UsageError("<name> and --file are mutually exclusive")` → `EXIT.USAGE` |
| `--input` lacks `=` or has empty key | `UsageError("invalid --input '<arg>': expected k=v")` → `EXIT.USAGE` |
| `--env` lacks `=` or has empty key | `UsageError("invalid --env '<arg>': expected k=v")` → `EXIT.USAGE` |
| `--cwd <path>` does not exist | `UsageError("cwd does not exist: <path>")` → `EXIT.USAGE` |

### 5.2 Repeatable-flag normalisation

citty (via mri) parses `--input k1=v1 --input k2=v2` as either `string | string[] | undefined` depending on count. The orchestrator normalises via a `toArray(value: string | string[] | undefined)` helper into a stable `string[]`, then maps through `parseKv`.

### 5.3 Path resolution

- `--file <path>`: relative paths resolved against `cwd = args.cwd ?? process.cwd()`. Absolute paths used as-is.
- `<name>`: looked up via `discoverWorkflows({cwd: resolvedCwd})`. Lookup is case-sensitive. Miss → `UsageError("workflow not found: <name>. Run \`aia workflow list\` to see available.")` → `EXIT.USAGE`.

## 6. Data flow

```
aia workflow run [<name> | --file <path>] [--input k=v]... [--env k=v]... [--cwd <path>] [--json]
        │
        ▼
command.ts (citty entry)
        │ args → opts (typed)
        │ wires SIGINT/SIGTERM → ac.abort()
        ▼
run-workflow.ts (slice orchestration)
        │
        ├── parseKv(toArray(args.input)) → Record<string, string>
        ├── parseKv(toArray(args.env))   → Record<string, string>
        ├── resolveCwd(args.cwd) → absolute path, validate exists
        │
        ├── resolveWorkflow.ts:
        │     │
        │     ├── --file <path>: parseWorkflow(resolve(cwd, path)) → Workflow + absolutePath
        │     │
        │     └── <name>:
        │           ├── discoverWorkflows({cwd}) → DiscoveryResult
        │           ├── workflows.find(w => w.name === name)
        │           │     │
        │           │     ├── miss → UsageError("workflow not found: <name>")
        │           │     └── hit  → DiscoveredWorkflow w
        │           └── return { workflow: w.workflow, absolutePath: w.absolutePath }
        │
        ├── runWorkflow(workflow, {
        │     inputs, env, cwd, signal: ac.signal,
        │     onEvent: (e) => receipt.emit(e),
        │     workflowFile: absolutePath, // for `local` uses: resolution
        │     // registryRoot defaults to <homedir>/.aiactions/actions/
        │   })
        │     │
        │     └── async, emits RuntimeEvents during run
        │
        └── return { result: RunResult, cancelled: ac.signal.aborted, workflowAbsolutePath }
        ▼
command.ts (post-run)
        │
        ├── receipt.finalize(result, cancelled)
        │     │
        │     ├── pretty: stderr summary line `✓ Run succeeded — N jobs, Mms`
        │     │           OR `✗ Run failed — N jobs (M failed)` OR `▼ Cancelled`
        │     │
        │     └── NDJSON: nothing extra to print (workflow-finished was already emitted)
        │
        └── exit code:
              if (cancelled)                       → process.exit(130)
              if (result.status === "succeeded")   → process.exit(EXIT.OK)         // 0
              if (result.status === "failed")      → process.exit(EXIT.RUN_FAILED) // 8
              // skipped doesn't happen at run-level in MS1 → would also exit 0
```

### 6.1 Re-parsing strategy in the name path

`DiscoveredWorkflow.workflow` is already a parsed AST. `runWorkflow` is invoked with `w.workflow` directly — no re-parse from disk. Trade-off: ~10ms saved; user-edits between `discoverWorkflows()` and `runWorkflow()` are not reflected. If a user wants a guaranteed fresh read, they can use `aia workflow run --file <path>`.

### 6.2 `workflowFile` propagation

`runWorkflow`'s `workflowFile` option is always populated with the resolved absolute path, regardless of whether the workflow uses any `local` `uses:` refs. This is a no-op cost for workflows without local refs and avoids a conditional branch.

## 7. Output rendering

### 7.1 Pretty mode (default)

Stream routing per `RuntimeEvent.kind`:

| Event | Stream | Format |
|---|---|---|
| `workflow-started` | stderr | `▶ Workflow run @ <iso-time>` |
| `job-started` | stderr | `  ▶ Job <jobId>` |
| `job-finished` (succeeded) | stderr | `  ✓ Job <jobId> (<duration>ms)` |
| `job-finished` (failed) | stderr | `  ✗ Job <jobId> (<duration>ms)` |
| `job-skipped` | stderr | `  ▼ Job <jobId> skipped — <reason>` |
| `step-started` | stderr | `    ▶ Step <stepId or index>` |
| `step-finished` (succeeded) | stderr | `    ✓ Step <id> (<duration>ms, exit <code>)` |
| `step-finished` (failed) | stderr | `    ✗ Step <id> (<duration>ms, exit <code>)` |
| `step-skipped` | stderr | `    ▼ Step <id> skipped — <reason>` |
| `step-stdout` | **stdout** | chunk passthrough (no decoration) |
| `step-stderr` | stderr | chunk passthrough (no decoration) |
| `workflow-finished` | stderr | `✓ Run <status> — <N> jobs in <duration>ms` |

If `ac.signal.aborted` is true post-run, the summary line is overridden with:

```
[stderr] ▼ Cancelled — N jobs skipped
```

### 7.2 NDJSON mode (`--json`)

All events serialized as `JSON.stringify(event) + "\n"` and written to **stdout** (one line per event, no decoration). `step-stdout` / `step-stderr` are NOT passthrough in JSON mode — they are emitted as RuntimeEvent records (the `chunk` field carries the UTF-8 content).

Example:

```
{"kind":"workflow-started","at":1730000000000}
{"kind":"job-started","at":1730000000005,"jobId":"hello"}
{"kind":"step-started","at":1730000000010,"jobId":"hello","stepIndex":0,"stepId":"say-hi"}
{"kind":"step-stdout","at":1730000000015,"jobId":"hello","stepIndex":0,"chunk":"hi\n"}
{"kind":"step-finished","at":1730000000020,"jobId":"hello","stepIndex":0,"stepId":"say-hi","status":"succeeded","exitCode":0}
{"kind":"job-finished","at":1730000000022,"jobId":"hello","status":"succeeded"}
{"kind":"workflow-finished","at":1730000000025,"status":"succeeded"}
```

stderr in JSON mode is otherwise empty — except for top-level CLI errors that fire BEFORE `runWorkflow` is invoked (UsageError, NotInGitRepoError, WorkflowParseError on resolution failure). Those still surface via the existing `cli.ts` handler with `✖ <msg>` to stderr.

Cancellation in JSON mode does NOT emit a synthetic event (S1-simplified design). Consumers detect cancellation via exit code 130.

### 7.3 Buffering / flushing

Both modes flush immediately on each event — `process.stdout.write` / `process.stderr.write` are synchronous on TTY and use natural Node back-pressure on pipes. No application-level queue.

## 8. Errors + exit codes + signal handling

### 8.1 `EXIT` enum delta

```ts
export const EXIT = {
  OK: 0,
  RUNTIME: 1,
  USAGE: 2,
  NOT_FOUND: 4,
  CONFLICT: 5,
  REGISTRY: 6,
  SCHEMA: 7,
  RUN_FAILED: 8, // NEW phase 6.5: workflow ran end-to-end but a step exited non-zero
} as const;
```

### 8.2 `EXIT_BY_BRICK_ERROR` delta

```ts
import { JobError, OrchestrationError, StepError } from "@aiactions/core";

// existing entries unchanged…

[JobError,           EXIT.RUNTIME], // NEW
[StepError,          EXIT.RUNTIME], // NEW
[OrchestrationError, EXIT.RUNTIME], // NEW
```

`RunnerError` (abstract) intentionally absent — never thrown directly. Concrete subclasses are mapped.

### 8.3 Exit code resolution order in `command.ts`

```ts
const ac = new AbortController();
const sigintHandler = () => {
  process.stderr.write("\n^C cancelling…\n");
  ac.abort();
};
process.on("SIGINT", sigintHandler);
process.on("SIGTERM", sigintHandler);

try {
  const { result, cancelled } = await runRunWorkflow({ ...opts, signal: ac.signal });
  receipt.finalize(result, cancelled);

  if (cancelled) process.exit(130);
  if (result.status === "failed") process.exit(EXIT.RUN_FAILED);
  // succeeded or skipped: exit 0 (default).
} finally {
  process.off("SIGINT", sigintHandler);
  process.off("SIGTERM", sigintHandler);
}
// Any throw bubbles to cli.ts top-level → EXIT_BY_BRICK_ERROR mapping.
```

### 8.4 Errors that bubble out of `runWorkflow`

- **`OrchestrationError`** — workflow refers `local` `uses:` but `workflowFile` not provided ; manifest validation failure ; unsupported runtime feature. → `EXIT.RUNTIME` (1).
- **`JobError` / `StepError`** — declared but currently unused at runtime ; mapped by anticipation.

A step exiting with non-zero status is NOT a throw — it propagates as `RunResult.status="failed"` → `EXIT.RUN_FAILED` (8). Distinction matters: runtime crashed (1) vs workflow's step failed (8).

### 8.5 Signal handling specifics

- `ac.signal.aborted === true` already at run start (Ctrl-C before any event) → runtime checks `signal.aborted` at top of each job iteration and marks every job `skipped`. Final `RunResult.status` may still be `"succeeded"` (the runner's status only flips to `"failed"` when a job's status is `"failed"`, not `"skipped"`). Exit 130 is taken in any case via the explicit `cancelled` check.
- Multi-SIGINT: `AbortController.abort()` is idempotent; second Ctrl-C is a no-op. No force-kill mode.
- Subprocess cleanup: runtime kills child processes via `subprocess.kill()` propagated by signal. Subprocesses receive SIGTERM then SIGKILL after a short timeout (runtime contract). No zombie risk if the runtime honours its contract.


### 9.2 `packages/cli/tests/commands/workflow/run/run.test.ts` (new)

Unit tests on the orchestrator + helpers + receipt:

1. **Argument validation** (4 cases): no name/file → UsageError ; both → UsageError ; invalid `--input` → UsageError ; invalid `--env` → UsageError ; invalid `--cwd` → UsageError.
2. **`parse-kv.ts`** (5 cases): `k=v` → `{k:"v"}` ; `k=v=w` → `{k:"v=w"}` ; `k=` → `{k:""}` ; `=v` → throw ; `k` → throw.
3. **`resolve-workflow.ts`** (4 cases): `--file <path>` → parses ; `<name>` discovered → returns with absolutePath ; `<name>` not discovered → UsageError ; `<name>` discovered with shadowed → returns project version (the "winner").
4. **`receipt.ts` pretty** (10 cases): one per event kind, asserting stdout vs stderr and the line format (use `vi.spyOn(process.stdout/stderr, "write")` capture pattern from phase 6).
5. **`receipt.ts` JSON** (2 cases): NDJSON line per event ; nothing on stderr.

### 9.3 `packages/cli/tests/bin-integration.test.ts` (extended)

End-to-end binary tests using `runCli` and tmp workflow YAML fixtures:

1. `aia workflow run --file <happy.yaml>` → exit 0, stdout has step's echo, stderr has summary.
2. `aia workflow run --file <happy.yaml> --json` → exit 0, NDJSON on stdout, expected event sequence (parse each line).
3. `aia workflow run --file <failing.yaml>` → exit 8 (RUN_FAILED), stderr contains "✗ Run failed".
4. `aia workflow run --file <happy.yaml> --input branch=main` → echo'd input visible (workflow uses `${{ inputs.branch }}`).
5. `aia workflow run --file <bad-schema.yaml>` → exit 7 (SCHEMA), bubbled `WorkflowSchemaError`.
6. `aia workflow run nonexistent` → exit 2 (USAGE), "workflow not found: nonexistent".
7. `aia workflow run` (no args) → exit 2 (USAGE), "expected <name> or --file".
8. `aia workflow run --file <happy.yaml> --cwd /nonexistent-xyz` → exit 2 (USAGE), "cwd does not exist".

### 9.4 Signal handling — manual verification only

Automated SIGINT injection into a spawned child is fragile and OS-specific. The verification gate at the end of the implementation plan includes a manual smoke step: run a slow workflow, hit Ctrl-C, confirm exit 130 and `^C cancelling…` on stderr.
